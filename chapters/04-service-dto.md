# Issue #4: PokeApiService と DTO 実装

API のレスポンスを、アプリ内で扱える形に変換します。

**DTO（APIの形）とドメインモデル（アプリの形）を分ける**のがこの章の肝です。
同じクラスを使い回すと、API の仕様変更がアプリ全体に波及します。

## 1. この章でやること

- `PokeApiService` に一覧取得・詳細取得のエンドポイントを定義する
- 一覧レスポンスには ID が無いので、`url` から切り出す
- 詳細レスポンスからタイプ・身長・体重・画像URLを取り出す DTO を定義する
- DTO → ドメインモデル → Entity の変換関数を用意する
- 151匹ぶんの詳細取得は、**同時実行数を制限した**並列処理で行う

## 2. 着手前に読む

- [Issue #4](https://github.com/sghh02/pokedex-android-kadai/issues/4) — **実装内容と受け入れ条件の正はこちら**。この章はそれを読む順番と、つまずきやすい点を補うものです
- [実装仕様](https://sghh02.github.io/pokedex-android-kadai/#04_実装仕様) — 5. PokeAPI の実装上の注意。151回の通信・単位・日本語名

## 3. つまずきどころ

- 151件を**無制限に並列**で投げないこと。API 側に負荷をかけるうえ、端末側もタイムアウトします。同時実行数を絞ってください（目安は全体で1分以内）
- タイプが1つのポケモン（ヒトカゲなど）で `type2` が null になるか、2つのポケモン（フシギダネ＝くさ／どく）で両方入るかを、実データで確認してください
- 途中で通信が切れても、取得済みのぶんは DB に残る作りにしておくこと。全部やり直しになる作りだと、テストのたびに1分待つことになります
